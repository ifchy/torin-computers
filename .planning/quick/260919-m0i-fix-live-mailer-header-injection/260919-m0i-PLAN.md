<objective>
Close the live email header-injection hole in `site-current/mailer.php` and ship it to the
production root at torin.bg.

`mailer.php:83` interpolates `$_POST['mail']` straight into `mail()`'s `additional_headers`
argument. `htmlentities()` — the only filter applied — does not strip CR or LF, and PHP does not
sanitise `additional_headers`. A POST carrying `%0D%0A` in the `mail` field therefore appends
arbitrary headers: `Bcc:` recipients, a forged `From:`. The mail leaves with torin.bg's own domain
and IP behind it.

Purpose: the realistic damage is reputational and it lands squarely on this project's core value.
The domain gets used to relay spam, lands on blocklists, and genuine customer enquiries start being
spam-filtered. A site whose whole job is "find a clear path to contact the shop" fails silently when
the contact path is filtered.

Output: a patched `mailer.php` live on `public_html/`, a single-file live-root deploy tool that
cannot upload a directory, a fresh verified backup, and a recorded before/after proof that the
injection worked and no longer does.

**Requirement ID:** this is unplanned production remediation with no ROADMAP requirement of its own.
It is tracked under the quick ID `QUICK-260919-m0i`. The endpoint is replaced wholesale by plan
04-05 at cutover; this patch exists because the hole is live *now* and cutover is not.

**Explicitly out of scope** — owned by 04-05, do not plan or build them here: honeypot field, rate
limiting, PHPMailer / authenticated SMTP, the unaligned-SPF deliverability problem, photo upload,
and the dead `msg.html` styling. Fixing the `From:` alignment is a *side effect* of the security
fix, not a deliverability workstream.
</objective>

<decisions>
**D-1 — The patch is written in PHP 5.2-compatible syntax, even though the root now runs 8.5.10.**
`filter_var`, `FILTER_VALIDATE_EMAIL`, `str_replace`, `array()` and the ternary all exist in 5.2 and
still work unchanged in 8.5. No `??`, no `[]` short arrays, no arrow functions, no typed params. The
root's PHP version changed *today*; a patch that only runs on 8.5 turns a version rollback into a
fatal error on the contact form. A patch that runs on both turns it into a non-event. This also
matches the tree-wide dialect rule at `src/includes/site-config.php:2`.

**D-2 — Strip CR/LF FIRST, then validate; validate exactly the bytes that will be emitted.**
Both orders reject a CRLF payload, so either "works". Strip-then-validate is chosen because the
string handed to `filter_var` is then byte-identical to the string written into the header — there
is no gap between what was approved and what ships. Validate-then-strip leaves a (here harmless, in
general dangerous) window where those two differ.

**D-3 — `From:` becomes a fixed literal on the shop's own domain: `TORIN.bg Message Form
<office@torin.bg>`.** Wording reused verbatim from the author's own commented-out line 72, so this
is restoring intent, not inventing copy. ASCII only — a Cyrillic display name in a raw header needs
RFC 2047 encoding, which is a new failure mode for zero benefit. Side effect worth naming: the form
stops sending *as the visitor* (a gmail.com `From:` from a bell.host.bg IP), which was SPF/DKIM-
misaligned. That is a bonus, not this plan's goal.

**D-4 — `Reply-To:` is emitted only when the sanitised address validates, and is omitted entirely
otherwise.** This preserves the owner's actual workflow (press Reply, reach the visitor).
**Accepted behaviour change, stated now rather than discovered later:** a visitor who *typos* their
email also loses the `Reply-To` header. Their address is still printed in the HTML table in the body,
so the owner can still reach them by copy-paste. Silently "repairing" a malformed address would be
guessing on the owner's behalf.

**D-5 — The injection proof uses a benign `X-Torin-Injection-Test:` marker header, never a real
`Bcc:`.** A `Bcc:` to a third-party address would mean actually relaying mail through production to
prove that production can relay mail. An `X-` header exercises the identical code path — the same
CRLF bytes, the same `additional_headers` argument — with zero delivery side-effect.

**D-6 — A NEW `scripts/deploy-live.sh`, not a parameterised `deploy-new.sh`.**
`deploy-new.sh`'s no-argument branch walks `find . -type f` over all of `src/` (line 161) and
uploads everything. Making its `REMOTE_ROOT` configurable puts that branch one environment variable
away from overwriting the entire production site with the not-yet-cut-over redesign — and `src/` is
being actively modified by a concurrent Phase 4 executor right now. Guarding that branch with a
conditional is a comment-level protection: it depends on a future reader not deleting the guard.
A separate script whose source **contains no directory-walk code at all** cannot do it regardless of
arguments or environment. That is the difference between discouraged and impossible, and Task 2
gates on the absence structurally (`grep -c 'find ' scripts/deploy-live.sh` -> 0).

**D-7 — Total live test sends: three.** One pre-patch (proves the hole is real), two post-patch (one
normal, one injection attempt). Every one carries an unmistakable automated-test label in both the
name and message fields. They all land in the owner's real inbox at office@torin.bg.
</decisions>

**PART A — patch `site-current/mailer.php`.**

Replace the four bare `$_POST` reads at lines 3-6 with guarded reads. Each of the four — `name`,
`mail`, `mobile`, `message` — becomes a ternary that yields the POST value only when the key is set
AND `is_string()` is true for it, and the empty string otherwise. Four `isset` guards and four
`is_string` guards, one per field, written out individually rather than factored into a helper: the
explicit form is what the gates count and what a future reader can see at a glance. `is_string` is
not decoration — on PHP 8.5 a bracketed field name posted as an array makes `htmlentities()` throw a
TypeError, which emits output, which breaks `header()` with "headers already sent". The guards keep
the measured `content-length: 0` baseline intact under hostile input, which is the whole point of
requirement 4.

Keep the four `htmlentities(..., ENT_QUOTES, 'UTF-8')` calls exactly as they are. Keep the `$ddddd`
date line, the entire `$m2` HTML body, the Bulgarian subject string and the `msg.html` redirect
byte-identical. This is a security patch; G6, G7 and G8 exist to prove nothing else moved.

Add a small helper function near the top named `torin_header_safe` taking one argument. It casts to
string, removes every carriage return, line feed and NUL byte using `str_replace` with an `array()`
of those three escapes, and trims the result. Define it with a `function_exists` guard so a future
include cannot collide with it.

Build the reply address before the headers: start `$reply_to` as the empty string; pass the guarded
`mail` value through `torin_header_safe`; then, only if the result is non-empty and
`filter_var($addr, FILTER_VALIDATE_EMAIL)` is not false, assign it to `$reply_to`. Strip first, then
validate — per D-2, so the validated bytes and the emitted bytes are the same bytes. A CRLF-bearing
string is not a valid address, so validation is the primary barrier; the strip is the independent
second barrier that holds even if a future edit weakens the validation.

Replace the two header-assignment lines. The first assigns a **fixed literal** From header on the
shop's own domain using the display name and address from D-3 — no variable interpolation of any
kind. The second appends the existing `Content-type: text/html; charset=utf-8` line unchanged. Then,
guarded by a check that `$reply_to` is not the empty string, append a `Reply-To:` header built by
concatenating the literal header name with `$reply_to`. Do not add `MIME-Version` — it is absent
today and the mail renders correctly for the owner; adding it is a behaviour change outside this
patch's remit.

After this, no header-assignment line may reference `$email`, `$from`, `$mobile` or `$question`.
That invariant is G1 and it is the plan's central gate.

Delete the dead commented-out blocks at lines 72-80 and 89-94. They are not being removed for
tidiness: they contain the address G5 counts and a `From:`-shaped string, so leaving them means a
gate that counts comments. This project has hit exactly that failure three times (03-03's word
count, 03-07's heading count, 03-09's EUR-in-"amateur" match). Line 94 additionally opens a string
that is never closed, inside a comment.

**Comment discipline for the patched file, non-negotiable:** no comment you write may quote any
string the gates count — not the address, not the Cyrillic subject, not `isset($_POST[`, not
`is_string($_POST[`, not `FILTER_VALIDATE_EMAIL` as prose. Describe them; do not reproduce them.
Comments explaining *why* CR/LF stripping and validation are both present are wanted, and they must
be phrased without the counted literals.

Purpose: upload one named, allowlisted file from `site-current/` to `public_html/` — the LIVE ROOT.

The four safety properties, all structural:

1. **No directory-walk code exists in the file.** There is no no-argument branch, no `find`, no
   recursion, no glob expansion over a source tree. Zero arguments is a hard error that exits
   non-zero with a message. This is what makes an accidental full-site overwrite impossible rather
   than discouraged, and Part C greps for its absence.
2. **A hardcoded allowlist array** of bare filenames, containing exactly `mailer.php` for now. Every
   argument must match an entry by exact string equality — not prefix, not glob, not `case`
   patterns. Because every entry is a bare filename with no separator, an argument containing a
   slash, a `..`, or a leading slash can never match, so path escape is impossible by construction.
   Reject non-matching arguments explicitly anyway and name the allowlist in the error.
3. **`TORIN_LIVE_DEPLOY_CONFIRM=1` must be present in the environment** or the script refuses and
   exits non-zero, printing what it would have done. A live-root write earns one deliberate speed
   bump; this makes an invocation recovered from shell history or tab-completion a no-op.
4. **No `--ftp-create-dirs`.** Nothing needs creating at the root, and its absence means a typo'd
   remote path fails loudly instead of quietly creating a stray directory on the production host.

No CSS-comment-stripping transform and no transforms of any kind: what is on disk is what goes on
the wire. Before each upload print the local path, its byte count, and the full destination URL.
After a successful upload print a one-line rollback reminder naming the snapshot path.
