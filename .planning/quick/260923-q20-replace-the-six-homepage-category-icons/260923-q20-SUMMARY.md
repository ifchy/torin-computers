# Owner illustrations replace the six category glyphs

Six SVGs supplied by the owner, mapped to the six homepage categories and processed before use.
Only `index.html:105` consumed the old glyphs, so the change is contained to the homepage.

## Process note — this record was written late

The planning artefacts for this task were not created before execution; the code was committed
first and this SUMMARY backfilled. Recorded rather than quietly fixed, because the GSD guarantee
that makes a quick task auditable is the artefact, and a task whose record is reconstructed after
the fact is weaker evidence than one written before. No work is missing — the three commits carry
the full reasoning — but the ordering was wrong.

## Three defects fixed before shipping, two invisible in the source

| | Defect | How it was found |
|---|---|---|
| 3 files | `preserveAspectRatio="none"` | read from the source; would have stretched every one, since the card box is 4:3 and the artwork is 1:1 and 1.23:1 |
| 3 files | opaque full-canvas background rects — **black** on cat-1, **white** on cat-5 and cat-6 | cat-1's was visible in the source; **the white pair only surfaced when rendered against the real tinted surface** |
| cat-2 | «HARDWARE ISSUE» baked in as outlined letter paths | visible in a render; located by bounding box |

The white backgrounds are the interesting one. Nothing in the source distinguished them from the
artwork's own white fills — they were only detectable by painting them against
`--c-surface-3` and looking. Removal is matched **structurally** (a rect spanning the whole
viewBox) rather than by colour, so a future file shipping one in a third colour is caught too.

## The lettering removal, and why it was safe

The site is Bulgarian-only by hard constraint, and at the 34px this renders at on a handset the
English lettering was an illegible smudge regardless. It was outlined paths, not `<text>`, so it
could not be edited as a string. Located by bounding box: 18 paths sharing one baseline
(y 758–843) spread evenly across x 621–1448 — 13 letter bodies plus 5 counters — at **contiguous
indices 7–24**. The contiguity is what made it verifiable rather than a guess.

The processor asserts 44 paths before, exactly 18 removed, 26 remaining. Any drift halts it
instead of silently shipping mangled artwork.

## Colour normalisation

Six near-miss blues → `#0547dc`, three ambers → `#fbad03`. Deliberate dark shading, the red
accent and every white left untouched.

**cat-3 and cat-4 needed no change at all** — they already carried the exact logo tokens. That is
independent corroboration of the Theme A decision taken earlier the same day (`260923-fno`).

## The latent CSS defect this uncovered

`.cat-card__media > img` has carried `height: 100%` since Phase 2 **and never got it**. A grid
item's `min-height` defaults to `auto` — the automatic minimum size — and for a replaced element
that floor is its own intrinsic height. Measured: an 80×80 image in the 80×60 box, overflowing by
20px and cut off by the `overflow: hidden` already on the box.

The artwork was being cropped **by the box** while `object-fit` believed it was fitting it, which
is why nothing about the object-fit declaration looked wrong. It affected the D-38 photo path
equally — a latent defect in a documented mechanism, never exercised because no photo was ever
swapped in.

First attempt was `place-self: stretch`, which measured **unchanged** at 80×80: stretch was not
the constraint, the minimum was. Four alternatives were tested (stretch, `grid-template-rows:
100%`, a block box, absolute positioning); all four work, and `min-height: 0` is the smallest.

## Verified

341×213), no horizontal overflow, no console errors. Card grid screenshotted.

### The incident, recorded because the fix is process not code

`index.html` was deployed **referencing six icon files that were still local**. All six returned
404 and the live staging homepage showed six broken images until a second deploy went out.

The deploy list had been derived from the files touched by the **most recent commits** rather than
from everything not yet on the server. The icon work had been committed earlier, the conversation
moved on to the cat-6 rewrite, and that pending deploy was never carried forward.

**Same root cause as the two-day staleness found earlier the same day.** `deploy-new.sh` uploads
and never deletes, keeps no manifest, and the origin holds no record of what it is missing — so an
incomplete deploy is invisible from both ends. The cutover sweep does not catch it either: it
passed 20/20 both before and after, because every assertion it makes is satisfied by a partial
deploy. **A 404 on a referenced asset is not something any current check asserts.**

Raised as ledger **55**. The fix closes both instances and needs no new infrastructure: assert
that every local asset referenced by a served page returns 200, and compare the committed tree
against what the origin serves. Until then — derive a deploy list from what is unshipped, never
from the latest diff.
