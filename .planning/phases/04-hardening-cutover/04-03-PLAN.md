<objective>
Make CONTACT-05 whole: the visitor attaches photographs of the damage, and the owner sees the
cracked screen on his phone.

Purpose: this is the detail that sold the notification channel — the owner sees the damage and
calls back with a price without opening a computer. It is also the single most dangerous thing
this phase adds, because this server maps `.html` to PHP, so any file that survives intact in a
web-reachable folder is code execution rather than a stray file.

Output: a server-side pipeline that treats every uploaded byte as hostile, a notifier that
branches correctly across zero / one / many photographs, and a dependency-free browser downscale
that makes the limits irrelevant in practice without ever becoming the limit.

**Decisions implemented (locked in CONTEXT.md):** D4-05 (photos delivered inline to the owner's phone — the detail that chose the channel), D4-12 (photos optional), D4-13 (up to five photographs, ten megabytes each), D4-14 (shrink in the browser, with a no-script fallback that simply enforces the server limit), and D4-15 (content-verified, re-encoded, randomly named).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| visitor browser -> `$_FILES` | Filename, extension and declared content type are all attacker-controlled. So are the bytes. |
| `upload.php` -> PHP temp directory | The only place an uploaded byte is ever written. Outside the document root by construction. |
| `notify.php` -> `api.telegram.org` multipart | Re-encoded bytes leave the machine. Nothing attacker-supplied reaches a shell or a filesystem path. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-12 | Elevation of Privilege | a malicious upload executed as code — acute here because `.html` is mapped to PHP | critical | mitigate | Nothing is written under the document root at all. Structural verification with `getimagesize()` plus `finfo`, full GD decode and re-encode (the only step that actually discards appended payloads and polyglot content), random filenames from `tempnam()`, and `unlink()` on every path. |
| T-04-13 | Denial of Service | resource exhaustion via large or many uploads | high | mitigate | Count, per-file and total byte ceilings enforced server-side before decode; `post_max_size` sized above 5x the per-file limit; the silently-emptied `$_POST` condition detected explicitly in 04-05. |
