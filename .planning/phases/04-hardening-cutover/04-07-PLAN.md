<objective>
Make service demand and contact-action use observable, without a cookie banner and without
touching the one interaction the business depends on — then delete the development scaffolding
that has been rendering on all 19 staging pages since Phase 2.

Purpose: the owner asked which buttons get used and which service pages get visited. Both answers
are available from a cookieless tool that needs no banner in front of a site whose entire premise
is getting a worried customer to their problem fast. The one real hazard is that the obvious,
documented way to instrument a phone link actively breaks it — the tracker prevents the default,
fires its beacon, and only re-navigates once that settles, which puts the dialer behind a
third-party round trip in a task that no longer carries the user gesture.

Output: one first-party listener file, one deferred third-party tag, twelve slot-labelled anchors,
a working funnel, and two deleted files.

**Decisions implemented (locked in CONTEXT.md):** D4-18 (a cookieless tool instead of the product the owner named — gated on his sign-off here), D4-19 (verify the free-tier limits against live terms before committing), D4-20 (no fallback to a cookie-setting product plus a banner), D4-21 (the four tracked questions), and D4-22 (session recording and a self-hosted application are both ruled out).
</objective>

  <decision>Ship a cookieless third-party analytics tool instead of the Google Analytics the owner explicitly asked for.</decision>
  <context>
    The owner asked for Google Analytics by name. This is a deliberate departure and the phase
    context says in as many words that it needs his sign-off. It cannot be settled by measurement
    and it should not be settled by the executor.

    The argument to put to him, in his terms: **he gets the same two answers he asked for — which
    buttons get used, and which service pages get visited — without a cookie banner in front of
    them.** The obligation that triggers a banner attaches to storing things on a visitor's device,
    not to counting visits. The analytics product he named always sets cookies, so it always needs
    a banner, which becomes the first thing a visitor sees on a site built around getting them to
    their problem fast; it costs roughly fifty kilobytes of third-party script against this phase's
    performance requirement; and it under-counts badly once people decline. A cookieless tool needs
    no banner, so there is nothing to be punished for — which is the constraint he stated himself.

    His hard constraint is no extra spend. The recommended tool's free tier is verified at 100,000
    events per month, one website, six months of retention, with custom events included — and a
    completed enquiry costs at most six events, so a local repair shop is nowhere near the ceiling.
    The two paid privacy-first alternatives were ruled out by that same constraint. A session-replay
    tool was ruled out because it records sessions and sets cookies, making it the most
    consent-hungry option available; a self-hosted option was ruled out because it is a full
    application needing its own security patching, which is the same ongoing burden this project
    rejected when it rejected a database-backed CMS.

    **One thing the research could not settle and this decision must:** whether the free tier's
    terms permit a commercial site. The pricing page describes the tier as suited to personal
    projects and low-traffic websites. If the terms restrict it to non-commercial use, the choice
    fails the no-spend constraint outright and option B or C applies.
  </context>

    **The declarative click-tracking attribute is forbidden on any phone or mail anchor.** Reading the
    shipped tracker's source shows that for any anchor carrying it, the tracker prevents the default,

    dialer after a third-party round trip, in a task that no longer carries the user gesture — delayed
    on a flaky mobile connection, and never at all where the browser enforces gesture-bound navigation
    for custom schemes. A manual test on a desktop passes this defect, because a phone link does
    nothing there either way.

    Author `src/js/analytics.js` in `site.js`'s exact style: an IIFE, strict mode, `var`, ES5-safe
    idioms, and delegated listeners registered at the document. One mechanism for every event on the
    site, including the ones where the declarative shortcut would have been safe — a second mechanism
    is how the two start to disagree.

    The click listener is **passive and capturing**, calls no default-prevention, awaits nothing, and
    returns immediately. It reads the anchor's slot attribute and fires the call event for a phone
    href and the write event for a contact-page href. The tracker's own transport survives navigation,
    so nothing is lost by not blocking. Guard every form handler behind a check that the contact form
    is present on the page, exactly as `site.js` guards on its own root element.

    The funnel handlers, each firing **once per page**: first focus on any form control; the first
    time at least one file is chosen; the first time the consent box is checked; and submit. Those
    four plus the two server-rendered events — the error render and the confirmation page — are the
    drop-off measurement: the step where the count falls is the step that loses people.

    **Event properties are a closed set.** The call and write events carry a slot name from the fixed
    list; the error event carries a field name from the fixed list. Nothing else. No submitted value,
    no free text, no identifier, ever — an event property is not a log line, and the difference
    between counting how many people abandoned and knowing who is one careless property.

    Add the slot attribute to **all seven rendered phone anchors**: the hero, the repeated call-to-action

    third-party connection in competition with the Cyrillic font preload, which is the
    largest-contentful-paint resource, and analytics never races the font. Wire `analytics.js` as a
    deferred first-party script through the asset-stamp helper, site-wide, because the phone listener

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| visitor browser -> third-party tracker origin | A script from a vendor's origin executes on every page and sends beacons. No integrity pin is possible on a script the vendor updates in place. |
| tracked DOM element -> event payload | Whatever the listener reads from an element leaves the browser for a third party. This is the property-scope boundary. |
| source tree -> server | Deleting a file locally does not delete it remotely; the deploy script uploads and never removes. |
