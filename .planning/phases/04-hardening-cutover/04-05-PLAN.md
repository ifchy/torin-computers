    nothing on include, with a header comment in `asset-version.php:1-4`'s voice.

    Four functions. `torin_verify_honeypot($post)` returns false when the decoy field is non-empty.
    `torin_sign_timestamp($ts, $secret)` returns a keyed SHA-256 HMAC of the render time, joined to
    the timestamp — this is the no-cookie alternative to starting a session, which is deliberately
    never used anywhere on this site because a session cookie would re-open the consent question the
    analytics choice was made to close. `torin_verify_timestamp($field, $secret, $minAge, $maxAge)`
    splits the field, recomputes the HMAC, compares it with a **constant-time** equality function
    rather than string equality, and then checks the age against both bounds. Set the lower bound at
    roughly three seconds and the upper at a couple of hours: the lower bound is what catches bots,
    the upper only needs to stop replay, and a tight upper bound rejects real people who leave a tab
    open. `torin_rate_limit_ok($ip, $secret, $limits)` implements a flat-file per-address throttle
    keyed on a SHA-256 of the address joined to a server secret, stored **outside the web root** —
    never an in-memory counter (there is no shared memory on this SAPI) and never a cookie (client
    controlled, and it re-opens the consent question).

    **No CAPTCHA and no visible challenge of any kind.** Recorded as a decision taken under the
    discretion grant so it is not revisited casually: a widget reintroduces exactly the third-party
    tracking problem the analytics choice avoids, it is a measurable conversion cost on the one form
    this business depends on, it is third-party payload against the performance budget, and the
    actual threat here is commodity form spam rather than a targeted adversary.

    Wire the guard into `src/contact-send.php` **before** field validation and before any outbound
    call, so a bot never reaches the network. Order: request-method gate, oversized-post detection,
    honeypot, timestamp, rate limit, then field validation. The oversized-post detection is its own
    step and not a fall-through: when the request body exceeds the server limit PHP discards the
    **entire** post array, so the handler sees an empty post and an empty files array and cannot
    tell "too big" from "no submission at all" — detect it as a non-zero content length with an empty
    post body and report it as too large.

    Every rejection writes a correlation-id line to the error log naming the reason, and **no
    submitted content**. This is what makes a false positive recoverable as a fact: nothing is
    stored, so a silently discarded genuine enquiry would otherwise be both unrecoverable and
    invisible in the same moment.

    In `src/includes/contact-form.php`, emit the signed timestamp into the hidden field the tracer
    already carries — it stops being a pass-through and becomes a real value.
