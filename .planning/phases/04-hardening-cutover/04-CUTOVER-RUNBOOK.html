Pre-flight gates — all resolved

Four questions that had to be answered before the swap could begin. All four were worked through on 2026-09-24. They are kept here with their outcomes, because two of them changed what the rest of this runbook says.

Resolved — and one was worse than the checklist guessed

The Search Console property turned out to be a URL-prefix property on http://www.torin.bg, verified by the HTML file method only. That is the worst of the four variants: it differs from the canonical target in both protocol and host, so publishing the canonicalisation would have flatlined the property holding sixteen months of history — during exactly the observation window. A Domain property now stands behind it.

  1. Identify what verifies the existing property answered

    URL-prefix property on http://www.torin.bg, verified by HTML file only — google1718743335455f1c.html.

    Corroborated rather than taken on trust: the token is live at the root (200, 53 bytes, correct body), there is no verification meta tag on either the live or the staging homepage, and DNS carried no google-site-verification TXT. The checklist's "something unidentified verifies an active property" is closed.

  2. Create a Domain property, verified by DNS TXT record live

    TXT added at the apex, confirmed present on both authoritative nameservers:

    google-site-verification=fIFCcniEjLBKQoRvVBLppDh8oiiMamRKLQcnzWGhev8
    CheckResult
    TXT at apex, straight from authoritative NSpresent
    Both nameservers agree (ns71 / ns72)1 each

    The hazard this avoided. The apex carries exactly one TXT record and it is the SPF on which all outbound mail depends. The rule was add, never edit — several TXT records at one name are fine, several SPF records are not, and a verification TXT is not SPF. Editing it by mistake would have broken the contact-form notification pipeline this entire phase exists to protect.

    Keep the old http://www.torin.bg property rather than deleting it. It will flatline after the swap, but its history stays readable and you will want it for comparison during the observation window.

  4. Owner sign-off on public commitments signed off

    The owner read uslovia.html and approved the wording. Two findings surfaced during that review.

    Fixed now — the footer label. It linked the page as «условия», but the page is wholly a Декларация за поверителност. Relabelled «поверителност» and verified on all 20 pages. The contact form's consent label needed no change: «условията за обработка на личните ми данни» was already scoped precisely to data processing.

§2

The swap

Server-side renames in both directions. No re-upload, a window measured in seconds, and the old site stays on disk as a live safety net. The order below is not a suggestion — a sitemap submitted early points a crawler at a state about to change, and a runtime setup not re-applied serves source on every page.

  1. Retarget the base URL, regenerate, redeploy — before the rename

    The swap re-uploads nothing. Whatever these files say at the moment of the move is what the live root publishes.

    a. In src/includes/site-config.php, change 'base_url' from https://torin.bg/new/ to https://torin.bg/. This is the only place the staging segment appears in a page-serving file, and every canonical link and breadcrumb URL on the site is built from it.

    b. Regenerate the sitemap with scripts/gen-sitemap.sh. Confirm 19 entries — not 20. msg.html is deliberately noindexed and the Google verification token is not a page; both are excluded by rule.

    c. Edit src/robots.txt by hand — change the Sitemap: line to https://torin.bg/sitemap.xml. Nothing regenerates this for you, and it is the second place in the tree encoding the staging segment.

    d. Run scripts/sitemap-check.sh offline. Checks D and E exist for exactly this moment. Both must pass before you go further.

    e. Deploy, naming the paths explicitly:

    # the three staging-segment files — the only ones left
scripts/deploy-new.sh includes/site-config.php sitemap.xml robots.txt

# scripts, icons, pages and footer: ALREADY DONE 2026-09-24
# js/*.js · img/icons/cat-{1..6}.svg · includes/footer.php
# mehanichni-problemi.html · zalivane-technosti.html
# all byte-verified against the origin
    Already deployed — nothing to do for these

    Comment stripping now runs on upload, so scripts ship without their rationale: analytics.js is 764 B gzipped against its 1024 B budget, and photo-resize.js went from six bytes of headroom to 574. All four match the origin byte-for-byte.

    Verified as working, not merely loading — a dead listener raises no console error either. A click probe against the served, stripped site.js confirms the nav opens, the list really becomes visible, a second click closes it and Escape closes it; a second probe confirms the relocated error-band focus still fires.

    Name the paths rather than running a bare no-argument deploy. A no-argument run uploads everything under src/ — a far larger blast radius than this step needs. It is no longer dangerous (the script now refuses the root .htaccess in code), but a deploy that names what it changes is one you can reason about afterwards.

  2. Regenerate the root's PHP wrapper silent if missed

    Corrected — the version half is already done

    PHP 8.5 is set account-wide, not just for /new/, and has been since 8.5 was adopted. Measured at the live root: curl -sI https://torin.bg/mailer.php → x-powered-by: PHP/8.5.10. There is no version risk in the move.

    The step survives for a different reason. What the account-wide selection does not do is put a wrapper in the root directory — and the promoted .htaccess names /home/torin/public_html/php.fcgi in three FcgidWrapper directives.

    ProbeStatusMeaning
    torin.bg/php.fcgi404absent
    torin.bg/new/php.fcgi200present
    torin.bg/error_log403exists, denied — calibrates the signal
    torin.bg/not-here.txt404absent — calibrates the signal

    403-for-denied and 404-for-absent are distinguishable here, so that 404 is a real absence rather than a deny rule. mailer.php proves .php runs on 8.5 at the root through the account handler with no local wrapper at all — but nothing proves .html does, and .html → PHP comes purely from that AddHandler/FcgidWrapper block. Every page on this site is .html.

    Moving the staging wrapper up is not enough — the trap

    /new/php.fcgi was fetched and read. The absolute path is inside the file, not just in its location:

    DEFAULTPHPINI=/home/torin/public_html/new/php85-fcgi.ini
exec /opt/cpanel/ea-php85/root/usr/bin/php-cgi -c ${DEFAULTPHPINI}

    Carried up by a later step it points at an ini that no longer exists — and php-cgi does not fail loudly on a missing -c. It falls back to the system ini. So the failure is not the 500 this step originally predicted; it is silent, and every limit the ini governs — upload_max_filesize, post_max_size, memory_limit — reverts to defaults. Those are exactly what the photo-upload pipeline depends on.

    cPanel → Select PHP Version → target public_html/ → re-apply 8.5 so the panel writes a root-correct php.fcgi + php85-fcgi.ini

    Or hand-correct the moved file's DEFAULTPHPINI line. Either way, verify by re-probing, not by reading the file.

  3. Move the current live root outside the document root

    Move it to /home/torin/old-site/. Not to public_html/old/.

    The distinction is the whole point

    A subdirectory of the document root publishes a complete crawlable copy of every retired page and of the unstaffed chat widget this project exists to remove. The old site must stay on disk. It must not stay reachable.

    Leave the §4 files where they are — do not sweep them along with the move.

  4. Move the staging contents up to the root

    Move public_html/new/* up to public_html/. Server-side rename; no re-upload.

  5. Upload src/.htaccess to the root by hand nothing else places it

    Corrected 2026-09-24 — this step used to say "confirm it landed"

    That wording was a trap, because an .htaccess will be sitting at the root after the previous step — the wrong one. Verified on the live origin today:

    Rewrite baseCanonicalisation target
    src/.htaccess (tree, promoted)/https://torin.bg/$1
    what staging actually runs/new/into /new/

    Proof rather than inference: https://torin.bg/new/covid.html follows to https://torin.bg/new/about.html. Under the promoted form it would land on https://torin.bg/about.html.

    deploy-new.sh refuses this file by design — hard error when named, skipped in a no-argument run. It has never been deployed and cannot be. A manual FileZilla upload is the only way it reaches the root. Moving /new/* up carries the /new/-form file there instead, leaving RewriteBase /new/ governing the live domain, every retirement redirect broken, and the canonicalisation pointing into a directory about to be deleted.

    Upload it, then read the file at the root by eye. Two things changed and one being right does not imply the other: the rewrite base must be /, and the canonicalisation substitution target must be the bare apex.

    This is not hypothetical. It shipped once: a relative substitution with no rewrite base made Apache build the redirect target from the filesystem path, and all four retired URLs answered a perfectly well-formed 301 pointing at https://torin.bg/home/torin/public_html/new/…, which 404'd on follow. Nothing in any build failed. Only following the redirect found it.

  6. Confirm the Search Console token is at the root

    google1718743335455f1c.html — 53 bytes, no trailing newline.

    Trap specific to this host: its .html extension means it is executed as PHP before being served. It must come back byte-identical, not merely exist. The sweep fetches and compares it rather than taking a 200 for an answer. Less critical than it was — the Domain property in §0 now holds verification independently — but the file is still what the old URL-prefix property hangs on.

  7. Confirm the wrapper files stop being publicly readable

    php.fcgi and php85-fcgi.ini both return 200 on staging right now — the wrapper discloses the account home path and the PHP binary path.

    The promoted .htaccess closes this with a FilesMatch block covering settings.txt, .user.ini, php.fcgi and php*-fcgi.ini, so the swap fixes it as a side effect. Confirm 403 afterwards rather than assuming the block landed.

  8. Remove the staging subtree — once the root is confirmed serving

    Not before.

Watch item during any panel visit

cPanel may write its own handler block into the root .htaccess, where it will coexist with the hand-written one. If pages start 500ing or serving as readable source after you touch the panel, look here first — the panel's block covers .php only, and every page on this site is PHP wearing an .html extension. Report what it added before changing anything.

§4

Leave these at the root

Do not move them, do not sweep them along with the old site.

  • .well-known/The certificate challenge directory. The TLS certificate renews within weeks of an autumn cutover, and a missing challenge path fails renewal silently until the certificate expires — by which point the whole site is untrustworthy in every browser.
  • cgi-bin/The host's script directory.
  • error_logHost-generated. It stays, and it stays refused over HTTP — the root is about to gain executing pages and a submission handler, so it will start accumulating entries that must not be publicly readable.
  • php.fcgiGenerated by the panel step in §2.
  • php85-fcgi.iniGenerated alongside it. Set display_errors = Off here at cutover — it is currently On, which renders PHP warnings, filesystem paths included, into the page for a visitor.
  • .user.iniOwner-edited; denied by the authorisation block.
  • settings.txtOwner-edited; denied by the authorisation block.

What the sweep cannot prove

That a phone dials, that an enquiry arrives, and that a search engine is happy. Those are §6.

Retire the transition guard — last

Confirm x-powered-by at the root does not report PHP 5.2. Only then delete the <IfModule !mod_fcgid.c> fail-safe from the root .htaccess. Expected to pass — the root already reports PHP/8.5.10 today. Run it anyway: the point is to confirm the fail-safe is not what is holding the site up.

It is kept through the swap on purpose: if the panel step in §2 is missed, the block degrades the failure from "20 pages served to the public as readable PHP source" to "still on 5.2, which is where we already were". A fallback quietly keeping 5.2 alive must never be allowed to pass as success.

The observation window

Read the success criterion correctly or it fails by construction

Google's own guidance is that consolidation after a host change takes a few weeks or more. Movement during consolidation is expected and normal. The criterion is no unexplained drops and no new missing pages — not no movement.

Watch the Domain property, not the old http://www.torin.bg one. That one will flatline by design the moment canonicalisation ships — it is not a signal, it is the expected consequence.

§7

Rollback

The same move in reverse, and it takes seconds. This is the entire reason the swap was designed as server-side renames rather than a re-upload.

  1. Move public_html/* back down to public_html/new/

  2. Move /home/torin/old-site/* back up to public_html/

  3. Restore the previous root .htaccess from the §1 backup

  4. Re-point cPanel → Select PHP Version back at public_html/new/

    So the wrapper path in the staging .htaccess resolves again.

  5. Re-fetch the homepage and confirm the old site is serving

One thing rollback does not undo

The canonicalisation redirects are a one-way door. Moving files back restores the content; it does not un-consolidate a search index that has begun following 301s to the apex. If the swap is rolled back, those redirects keep pointing at the apex — which is still correct for the old site, since it is served on the same four variants. Rolling back the content is cheap. Rolling back the canonical host choice is not, and is not attempted here.
