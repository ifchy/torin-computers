<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Choose the canonical host, and the order of operations</name>
  <decision>Which host form becomes canonical, and in what order the redirect and the reporting property are established.</decision>
  <context>
    **This is the one-way door in this phase.** Once the redirects are published and the search
    engine consolidates onto the chosen host, switching to the other form means a second
    consolidation across the whole site and real ranking disturbance. This is not a preference that
    can be revisited cheaply after launch, which is why it is gated here rather than decided inside
    an implementation task.

    **The measured situation, as of the phase research:** all four protocol and host variants return
    success with **no redirect at all**, so the same content is served on four hosts and ranking
    signals are split four ways. The variant that Search Console shows as actually indexed and
    ranking is the insecure, prefixed form — the least preferred of the four — carrying the only real
    traffic figure this project has ever had. Meanwhile the build's own configuration already
    declares the secure, unprefixed form as the base URL. Choosing the unprefixed secure form means
    **nothing in the build changes**; choosing the prefixed form means changing the base URL entry
    and regenerating the sitemap, and it means canonicalising onto a form that is worse on both axes.

    **The ordering matters as much as the choice.** In a URL-prefix property those four variants are
    four *different* properties. The moment the redirects go live, traffic moves to the canonical
    form and the old property's graphs fall to zero — during exactly the window in which this phase's
    success is judged by watching for new errors and ranking drops. The property that will carry the
    traffic must therefore be created and verified **before** the redirects are published, not after.
    A domain-level property unifies all four variants and is immune to any file move, but needs a
    DNS text record and therefore panel access that is currently unconfirmed.

    Also worth stating plainly so the success criterion is not read as failing by construction: the
    search engine's own guidance says consolidation takes a few weeks or more, and that no
    change-of-address tool is involved for a protocol or prefix move on the same domain. Movement
    during consolidation is expected and normal — the criterion should be read as no *unexplained*
    drops and no new missing pages, or it cannot be met.
  </context>
  <options>
    <option id="option-a">
      <name>Secure, unprefixed host is canonical; the other three redirect into it (recommended)</name>
      <pros>Nothing in the build changes — the configuration already declares it. Secure and shortest form. One hop from any of the four variants, using a rule shape already proved to work on this host.</pros>
      <cons>The ranking history sits on a different variant and must consolidate across; a new reporting property has to be created and verified before the redirects ship, or the launch window is unobservable.</cons>
    </option>
    <option id="option-b">
      <name>Secure, prefixed host is canonical</name>
      <pros>Closest to the form that currently ranks, so consolidation may settle marginally faster on that one axis.</pros>
      <cons>Requires changing the base URL entry and regenerating the sitemap; still a protocol change from the ranking variant, so consolidation happens regardless; canonicalises onto the longer form for no lasting benefit.</cons>
    </option>
    <option id="option-c">
      <name>Defer host canonicalisation past launch; ship the swap with four variants still live</name>
      <pros>Removes the one-way decision from launch day and shortens the change under review.</pros>
      <cons>Leaves the defect that has gone unseen for three phases in place at the exact moment the site's content changes completely — four hosts serving identical new content, signals split four ways, and a second disruptive consolidation to do later anyway. Recommended against.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c. Also state whether DNS record editing is available, and confirm the reporting property that will carry post-launch traffic has been created and verified BEFORE any redirect is published.</resume-signal>
  <reversibility rating="one-way">Once the redirects are published and consolidation begins, reversing means a second consolidation across the whole site with real ranking disturbance. This is the phase's single one-way door and is the reason this checkpoint exists.</reversibility>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet -> the server config at the document root | One file governs redirects, runtime handling, access denials and caching for the entire site. Its failure mode is the whole site at once. |
| request host header -> redirect substitution | The classic open-redirect and host-header-injection surface, already prohibited in the current file and at risk of being lost in the promotion edit. |
| the reporting property -> the ability to observe the launch | Not a security boundary, but a visibility one: after the redirects ship, the wrong property reports zero. |
| the old site on disk -> public reachability | Where the old root is moved to decides whether a complete crawlable copy of every retired page remains fetchable. |
