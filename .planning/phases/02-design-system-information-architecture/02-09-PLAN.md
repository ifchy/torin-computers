Close **G-02-4**: the web-font swap displaces the two hero CTA buttons by 27.1px.

Measured by `scripts/probes/font-swap.js` at 360x640: the CTAs move **27.1px upward** when Sofia
Sans arrives, against an 8px threshold. The h1 renders **110.4px** in the fallback stack and
**73.6px** with Sofia Sans. The owner chose **option 3 — reserve space for the heading** — over
`font-display: optional` (which would leave slow first visits permanently in the fallback face) and
over accepting it.

**The mechanism is a metric-adjusted fallback, and a `min-height` is specifically the wrong tool.**
The fallback needs *more* lines than the web font, not fewer, so a min-height sized to Sofia Sans is
overflowed by the fallback rather than absorbing it.

**The arithmetic reproduces the measured number exactly, and it tells you what "fixed" looks like.**
Worked from the deployed values:

| Term | Value | Source |
|---|---|---|
| `--fs-display` at 360px | 32px | `clamp(2rem, 1.55rem + 2vw, 3rem)`; 1.55rem + 2vw = 24.8 + 7.2 = 32px, equal to the 2rem floor |
| h1 line box | 36.8px | `line-height: 1.15`, unitless — metric-independent |
| h1 heights | 73.6px = 2 lines · 110.4px = 3 lines | measured; consistent with the line box above |
| h1 content box at 360px | 328px | gutter `clamp(1rem, 4vw, 2rem)` resolves to 1rem each side; `.hero__inner` max-width 34rem does not bind |
| swapped content stack | 233.4px, under the 268.8px min-height | `02-RENDERED-VERIFICATION.md` D-30 |
| fallback content stack | 233.4 + 36.8 = **270.2px**, over 268.8 | derived |

`.hero` is `display: grid; align-content: center`. In the swapped state the stack fits, so the hero
is 268.8px tall and the content is centred with an offset of (268.8 − 233.4) / 2 = **17.7px**. In
the fallback state the stack does **not** fit, so the hero becomes content-sized and the offset
collapses to the 8px `padding-block`. The CTA delta is therefore
(17.7 + 73.6) − (8 + 110.4) = 91.3 − 118.4 = **−27.1px** — the measured value, to the tenth.

So the fix condition is precise: **make the fallback h1 two lines.** Both stacks become 233.4px, both
heroes 268.8px, both offsets 17.7px, and the predicted CTA delta is **zero**. The gate threshold is
8px; anything nonzero means something other than the h1 also moved and must be explained rather than
tolerated.

Because every line-height in this design is unitless, block height depends only on line COUNT, which
depends only on advance width — so `size-adjust` alone is the lever, and the ascent/descent
overrides that usually accompany it cannot change a single measured height here.

**One further input to the line count, named because it is silent and lives outside the font code.**
`src/css/base.css:136` sets `text-wrap: balance` on `h1, h2, h3`. The hero heading is therefore not
greedy-wrapped: the engine minimises the raggedness of the two-line result rather than filling the
first line to 328px and pushing the remainder down. That does not change the arithmetic above — a
two-line block is 73.6px and a three-line block is 110.4px however the break is chosen — and it does
not compromise the measurement, because the calibration probe substitutes `font-family` on the live
`h1` and `font-swap.js` measures the live `h1`, so `balance` is in force identically in the scan and
in the gate. It matters for two other reasons: it is what makes "the widest adjustment that still
sets two lines" a *balanced*-fit threshold rather than a greedy-fill one (see the asymmetry section
below), and it means **removing `text-wrap: balance` in a later phase would invalidate the shipped
percentage without touching a single line of font code**. That is why task 2's mandated derivation
comment must name it.

## Why `size-adjust` and not the usual accompaniment

Recorded here because the obvious next move for a reader who knows this technique is to add three
more descriptors:

`ascent-override`, `descent-override` and `line-gap-override` exist to make the fallback's LINE BOX
match the web font's when the line box is derived from font metrics — that is, when `line-height` is
`normal`. This design system sets a unitless `line-height` on every text element (1.15 on h1, 1.20 on
h2, 1.25 on h3, 1.30 and 1.40 on components, 1.65 on body, 1.2 on buttons) and `grep -rn
'line-height:\s*normal' src/css/` returns nothing. Every line box is therefore already
metric-independent, and the only thing that can change a block's height is how many lines the text
occupies. `size-adjust` — which scales advance widths — is the entire mechanism, and the three
overrides would be decoration.

## The asymmetry that sets the safety margin

One percent too wide costs a whole 36.8px line the moment the balanced two-line layout no longer
fits — with `text-wrap: balance` in force (`base.css:136`) that is the point at which the engine can
no longer distribute the string across two lines of at most 328px each, not the point at which a
greedy first line overflows. Too narrow costs nothing until the string would collapse from two lines
to one, which at 32px/700 across 36 Cyrillic characters would need roughly a halving of the advance
width — far outside any plausible scan result. The margin therefore goes on the narrow side, and the
shipped value sits below the widest value that still measures two lines rather than at it.

Because the threshold is a *balanced*-fit threshold rather than a greedy-fill one, it is measured
rather than computed: no advance-width ratio predicts it, which is why the scan in task 1 is the
authoritative measurement and the width ratio is only a companion reading. It is also why
`text-wrap: balance` is a load-bearing input to the shipped percentage despite living nowhere near
the font code, and why the derivation comment must name it.

## Known-open, deliberately not closed here

- **Only fonts installed on the measuring machine can be calibrated.** `Segoe UI` (the current
  Windows fallback) and `Roboto` (the Android fallback) are not installed here and their ratios
  cannot be measured. Both are narrower than Arial, so an Arial-calibrated adjustment applied to them
  errs on the safe side — same line count or fewer, never more. That is a reasoned expectation, not a
  measurement, and the SUMMARY must say so rather than implying site-wide coverage.
- **`size-adjust` support.** Chromium, Firefox and current Safari support it; an older engine ignores
  the descriptor, the adjusted face resolves at 100% or not at all, and the rendering is exactly
  today's. The fix can no-op, never regress.
- **G-02-1b (category icon redraw) is DEFERRED to Phase 3** and is not touched by this plan.
- **This plan's gate depends on a URL that plan 02-08 owns.** `font-swap.js` blocks fonts by the
  glob `*.woff2`, which a query string defeats, so the G-02-4 measurement only works while the Sofia
  Sans preload stays unstamped. Plan 02-08 excludes it deliberately and records this as the second
  of its two reasons; this plan records it in the calibration probe's header and in the shipped
  `base.css` comment. A stamped woff2 would not fail this gate — it would make it report
  `maxAbsDeltaPx: 0` and pass. Neither plan fixes the fragility (the glob is CDP's, and blocking by
  request type would be a change to a probe this plan is forbidden from reinventing); both record it
  so a future change to either side is visible from the other.
- **`text-wrap: balance` (`base.css:136`) is an input to the shipped percentage and is not owned by
  this plan.** It applies to `h1, h2, h3` sitewide, and the calibrated value is the widest adjustment
  at which a *balanced* two-line hero still fits. Removing or overriding it in a later phase would
  invalidate the calibration without touching any font code. Not changed here, named in the shipped
  comment, and asserted present by the record gate in task 2.
