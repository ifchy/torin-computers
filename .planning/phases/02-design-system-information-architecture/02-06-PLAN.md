## Design decision: why `<noscript>` rather than shipping the nav open

The orchestrator's preferred shape was to ship the nav open in the served markup and let `site.js`
collapse it on load. That is the purer statement of progressive enhancement and it was evaluated
first. It was rejected on one hard constraint, and the reasoning is recorded here so it is not
re-litigated as an oversight.

| | Ship open, JS collapses | `<details>` / `:target` control | `<noscript>` override (**chosen**) |
|---|---|---|---|
| Works with scripting off | Yes | Yes | Yes |
| Works when scripting is on but `site.js` fails to load | Yes | Yes | **No** — the one genuine weakness |
| Flash of open-then-collapsed nav on every page load | **Yes, inherent** | No | No |
| Requires a second script (inline, render-blocking, in `<head>`) to suppress the flash | **Yes** | No | No |
| Keeps `site.js` as sole writer of the disclosure attribute | Yes | **No** — state moves to `[open]` | Yes |
| Keeps the existing ARIA contract and `site.js` unmodified | Partly — init changes | **No** — full rewrite of a verified 60-line file | Yes |
| Undo cost | Revert markup + JS init | Revert markup + JS + CSS | Delete one file and one line |

The flash is not a cosmetic worry. Any approach whose served paint state differs from its
JS-settled state must transition on load, and the nav sits at the very top of the body where
progressive rendering paints earliest — so on a slow connection the whole page content shifts down
and snaps back on every one of sixteen pages. The only way to suppress it is a render-blocking
inline script in `<head>` that marks the document as scripting-capable before first paint, which
adds a third `<script>` element to a tree whose entire script surface was enumerated during
verification, costs first-paint time on every page, and introduces a second writer of
nav-adjacent state — the same class of dual-source-of-truth the project banned for the disclosure
attribute.

`<noscript>` has no transition by construction: the user agent either parses its contents and
applies the override from first paint, or never sees them at all. There is no timing involved.

Its one real weakness is honest and recorded: **if scripting is enabled but `site.js` fails to
load or throws, the nav stays hidden below 56.25rem.** That failure mode is narrower than
scripts-blocked (the file is same-origin, 2,476 bytes, and its absence would already be visible as
a 404 in the deployed-asset sweep), and closing it requires exactly the capability-marker approach
rejected above. It is registered as a residual gap rather than silently ignored.

is a long-established pattern, but this project has no browser matrix and no automated rendering
harness. **No source read can prove the rendered outcome.** The mechanism is asserted
programmatically from source and from the deployed response; the rendering is asserted by a
`human-check`. If that check fails, the fallback position is the `<details>` rewrite, not a
weakening of the criterion.

Unconditional rules, in this order:

- `.nav__toggle { display: none; }` — the hamburger cannot function without script. Hiding it is
  load-bearing, not tidiness: it carries a collapsed-state ARIA attribute in the served markup, and
  leaving it visible over an open list would announce the opposite of what is rendered. `display:
  none` removes it from the accessibility tree so nothing false is announced.
- `.nav__disclosure { display: none; }` — same reasoning for the Услуги button.
- `.nav__list { display: block; }` — reverses the mobile hide.
- `.nav__sub { display: block; }` — reverses the sub-list hide; at this width the sub-list is
  already static and already has its own inset padding, so nothing else is needed.

Then one `@media (min-width: 56.25rem)` block. Use `min-width` only, never `max-width` — that is a
documented convention of this stylesheet set (see the breakpoint comment at `components.css:721`)
and the same breakpoint value must be reused verbatim so no two adjacent breakpoints can both match
or both miss:

- `.nav__list { display: flex; flex-wrap: wrap; }` — restores the desktop horizontal row that the
  unconditional `display: block` above would otherwise destroy for no-script desktop visitors, and
  permits the sub-list row to wrap below it. Only `display` needs restating; every other desktop
  declaration on `.nav__list` still comes from `components.css`.
