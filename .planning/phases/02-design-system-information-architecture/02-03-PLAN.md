<objective>
Give the site its navigation and its contact surface: a flat five-item nav with the six
categories in one single-level disclosure, and a compact contact-first footer carrying the
shop's real coordinates in both human and machine-readable form.

Purpose: IA-02 is the half of the information architecture the card grid cannot deliver. The
six Bulgarian category names total 142 characters, which cannot sit inline in a desktop nav
bar alongside a logo — a six-item disclosure is the answer, and it is emphatically not the
dense mega-menu IA-02 prohibits. The footer is where D-33 and D-34 put the shop's address,
three phone numbers, hours and Maps link, replacing a several-hundred-kilobyte third-party map
iframe with a deep link plus JSON-LD.

This plan also carries the phase's entire JavaScript surface: roughly fifty lines of vanilla
JS. Alpine.js was deliberately rejected — it would ship as about 44 KB raw on a host that
serves nothing compressed, to replace fifty lines, and it reintroduces exactly the class of
attribute-driven runtime framework DESIGN-01 exists to remove.

Output: every page gains its nav and its footer, and the shop becomes machine-readable to
local search.
</objective>

<assumption_delta_decision>
**Signal:** `pluralization` — `$site['phone']` currently holds one comma-joined string
(`'02 9549710, 088 9458404, 087 9128244'`) while the UI-SPEC requires three separately
tappable `tel:` links rendered by looping the config.

**Noun now primary:** the **list of phone numbers**, not "the phone number".

**Decision: promote.** `phone` is replaced by `phones`, a list of three, and the scalar is
removed rather than kept alongside. Keeping both would leave two representations of the same
fact that can silently disagree the day a number changes — and the whole reason this value
lives in `site-config.php` is that it is single-sourced. The list is the general
representation; a single number is now just the one-element case of it.

**Why this is safe to do here:** 02-PATTERNS flagged this as a two-file hazard, because
`header.php` echoed the scalar and would print `Array`. Plan 02-01 already removed that echo
when it moved contact chrome to the footer per D-33, so at this point the only consumer is the
footer this plan writes. Nothing else reads the value. The hazard was sequenced out rather
than worked around.

**Invariant worth encoding:** no consumer may join the list back into a display string —
each entry must produce its own `tel:` link, so the layout renders one number or five equally
well.
</assumption_delta_decision>

The toggle must be a `<button>`, never an anchor with a fragment href. Do **not** use
`role="menu"` or `role="menuitem"`: the W3C APG is explicit that a navigation dropdown is the
Disclosure Navigation pattern, and `role="menu"` makes screen readers announce a desktop
application menu and hands navigation to arrow keys — wrong for six links, and a common
damaging mistake. Do **not** implement arrow-key navigation for the same reason.

Mark the current page with `aria-current="page"`. Derive the current filename from
`basename($_SERVER['SCRIPT_NAME'])`, **not** from `$_SERVER['PHP_SELF']` — the latter carries
client-supplied path info and is a classic reflected-XSS vector. Use the value only for
comparison; never echo it.

D-20's sales-line grouping is satisfied by the pair of routes: the nav item points at
`laptopi.html`, and the footer's secondary link row (Task 2) carries both «лаптопи» and
«резервни части», so both sales pages are reachable from every page on the site.

**`src/js/site.js`** — the entire JavaScript surface of the phase, roughly 35 lines, wrapped
in an IIFE with `'use strict'`, loaded from `header.php` with `defer`. Implement exactly the
behaviour 02-RESEARCH §3a specifies: query every element inside the nav carrying both
`aria-expanded` and `aria-controls`; clicking one closes the others and toggles its own state;
`Escape` anywhere in the nav closes the open disclosure **and calls `focus()` on its
controlling button** (this is required by WCAG 2.1 SC 1.4.13, not optional polish); a
`focusin` outside the nav closes everything; a click outside the nav closes everything. The
script's only DOM writes are `setAttribute('aria-expanded', ...)` and `focus()`. It must not
assign markup into the document and must not evaluate strings as code.
<!-- planner-discipline-allow: innerHTML -->

Attach no hover handlers. Click and tap only, at both breakpoints — hover-opened menus are the
classic source of the "it opened when I was just moving past it" complaint and are unusable on
touch.

**`src/css/components.css` — nav styling.** Every visual state selects off
`[aria-expanded="true"]` and **never off an `.is-open` class**. This is the structural
guarantee that the announced ARIA state and the rendered state cannot desynchronise, which is
the single most common bug in hand-rolled dropdowns — the JavaScript writes only the attribute,
so there is no second source of truth to fall out of sync.

Mobile-first: `.nav__list` and `.nav__sub` both `display: none`, each revealed by the adjacent
`[aria-expanded="true"]` sibling selector. At `min-width: 56.25rem`: hide `.nav__toggle`, make
`.nav__list` a flex row with `--sp-xl` gap, and make `.nav__sub` absolutely positioned with
`min-width: 22rem`, `max-width: 26rem` and `z-index: 20`. The 22rem floor is deliberate and
computed — 02-RESEARCH proposed 20rem, and UI-SPEC C-3 shows the 33-character category name
measures about 289px against a 288px content box at that width, so it wraps by a hair.

Dropdown surface `--c-surface-2`, `--r-lg`, `--sh-2`, `--sp-md` padding. Each dropdown item at
`--fs-body` with `min-height: 44px`, `--sp-md` inline padding, and a `--c-surface-3` hover and
focus fill. The chevron rotates 180 degrees under `[aria-expanded="true"]` over `--dur-fast`.
The active top-level item gets `--fw-bold` plus a 3px `--c-brand` keyline underneath — one of
the six permitted amber uses. Every interactive control has a hit area of at least 44 by 44.

Below `56.25rem` the panel is **in flow**, full width, pushing content down. Do not build an
overlay or drawer: that would need focus trapping, background inerting and scroll locking —
three more things to get right for a five-item nav — and would fork the ARIA contract into a
second implementation that always rots first.

The header is **not** sticky (UI-SPEC §Component Contract 2). A sticky header would eat 56px
of mobile viewport and fight D-30's above-the-fold arithmetic; the sticky call bar from plan
02-02 already provides persistent reachability, and it carries the actual conversion actions.

**Known accepted gap, do not silently solve:** with JavaScript disabled, `aria-expanded` stays
`false` and the six category links are unreachable *from the nav*. The mitigation is
structural — every category is reachable from the homepage card grid by construction (IA-01),
and the homepage is one click away via «Начало». Do **not** build a CSS-checkbox fallback: it
would fork the ARIA contract for a case the card grid already covers. Record the gap in the
SUMMARY rather than treating it as closed.

Deploy `includes/`, `js/` and `css/` to `public_html/new/` and run the live checks.
