<objective>
Close **G-02-1**: a deployed stylesheet change cannot invalidate a cached copy.

The stylesheets as deployed are **correct**. The owner reported a completely broken desktop
rendering — nav stacked in a column with the Услуги sub-list permanently open, no card treatment,
icons at full-viewport size — and a hard reload restored it entirely. The defect is not in the CSS;
it is that `<link rel="stylesheet" href="css/components.css">` carries no version, while the origin
serves that file with `cache-control: max-age=604800`. A visitor who loaded the page mid-iteration
holds a stylesheet from a state where the card grid and nav rules did not yet exist, and there is no
remote way to flush it for seven days.

**The severity was corrected downward and that correction is load-bearing here.** This was
originally called a blocker on the reasoning that returning torin.bg customers would get new HTML
with old CSS at cutover. That reasoning is retracted: the legacy site and the new site share no CSS
filename and no CSS directory, so at cutover nobody holds any of the new files cached. What remains
real — hence major — is that staging review is unreliable while `/new/` is iterated several times a
day, and that every CSS edit *after* launch leaves returning customers stale for up to a week.

The mechanism is `?v=<filemtime>` stamped on the href by the shared head. The pages are already PHP,
so this needs no build step, no new dependency, and no rename discipline. The owner's own suggestion
— rename the file per version — also works, and is recorded here as the fallback if query-string
invalidation ever proves unreliable on this host; it is not chosen because it is manual and every
manual step is a step someone eventually skips.

**A second, equally important defect is closed alongside it.** Every rendered check this phase ran
reached the origin with a cache-busting query string. That bypassed the very cache that produced this
gap, so the automated verification measured a state no returning visitor sees and could never have
caught this class of defect. This plan commits a checker that fetches with **bare URLs**.

Purpose: a CSS edit reaches the browser that needs it, on the next request, without a hard reload.
Output: one new PHP function library, five stamped URLs in the shared head, a staging-bounded cache
lifetime, and a committed non-cache-busted gate over all sixteen deployed pages.
</objective>

`filemtime()` and Apache's `Last-Modified` read the same inode stat, so the emitted token and the
response header are the same number by construction **whenever the helper stat'd the same file the
origin serves**. That is what the equality assertion in task 3 actually tests: **path resolution**,
not freshness. It catches a stamp computed against a path that does not exist on the server or
against the wrong copy of the file (and, via the `?v=0` sentinel, a stat that failed outright), and
it is a real test of those because the script asserts an equality it does not itself compute.

It cannot detect a **frozen** stamp: freezing moves `filemtime()` and `Last-Modified` together, so
the two stay equal and the assertion still passes. Freeze detection is a separate check — task 3's
byte-identical redeploy of `js/site.js`, which must MOVE the emitted token. Keep the two claims
distinct in the SUMMARY; collapsing them into "the equality proves the stamp is live" overstates
what the equality can see.

  including the default Theme B. Confirmed live: `curl -s https://torin.bg/new/index.html | grep -c
  'theme-a.css'` returns 1 today, with no cookie and no `?theme=a`. It is harmless in effect —
  `src/css/theme-a.css` is fifteen lines containing exactly one `[data-theme="a"]` block, so a
  Theme-B page fetches a stylesheet none of whose rules can match — but it is one wasted request per
  page load, and it is a live wrong-condition bug regardless.

  **It is out of scope here** and must not be fixed in this plan: the fix is a one-line move inside
  the file that Phase 4 deletes outright, and it is not what G-02-1 is about. It is recorded because
  **task 2's assertion depends on it**. Task 2 asserts exactly one stamped `theme-a.css` href on the
  *default* homepage; that passes only because the link is unconditional, and moving line 34 inside
  the branch would flip that assertion from 1 to 0 without anything actually breaking. Task 3's
  committed gate therefore treats the same link as **conditional** — stamped if present, no failure
  if absent — so the durable checker survives both the eventual fix and the Phase 4 deletion. The two
  tasks assert different things about the same link on purpose, and this is the reason.
- **The checker proves the emitted URL, not the browser's cache eviction.** `curl` does not cache, so
  a bare-URL fetch demonstrates that a version token is present, live and resolvable — it does not
  itself demonstrate that a browser discards the old file. The token *is* the mechanism by which the
  browser does so (a different URL is a different cache entry), and the bounded max-age is the
  backstop. Stated here so the SUMMARY records what was proven rather than overclaiming.
- **The token is an mtime, not a content hash.** A redeploy of byte-identical files therefore bumps
  the token and warms caches unnecessarily. That is the tradeoff of the mechanism the UAT
  recommended, it costs a few KB on a low-traffic brochure site, and a content hash would mean
  reading and digesting every stylesheet on every request on a PHP 5.2 shared host with no reliable
  opcode/user cache. Recorded, not fixed.
