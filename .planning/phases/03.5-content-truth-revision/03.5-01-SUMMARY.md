### Check 4 — the defect this checkpoint existed to catch

First run, all four URLs:

```
covid           301 -> https://torin.bg/home/torin/public_html/new/about.html                    -> 404
laptopi         301 -> https://torin.bg/home/torin/public_html/new/index.html                    -> 404
rezervni-chasti 301 -> https://torin.bg/home/torin/public_html/new/ekran-klaviatura-portove.html -> 404
za-bateriite    301 -> https://torin.bg/home/torin/public_html/new/zalivane-technosti.html       -> 404
```

The status line was `301` and a `Location` header was present on every one — so the plan's own check
command, which greps only `^HTTP/` and `^location:`, **would have passed this**. Only following the
redirect exposed it. The directory's filesystem path had leaked into a public URL.

Cause: in a per-directory `.htaccess` a relative substitution has no URL-space base to resolve
against, so an external redirect builds its `Location` from the filesystem path. The block's comment
asserted the opposite and had never been measured. `RewriteBase /new/` added; the comment rewritten
to record what actually happened.

After `82deb04` and a one-file redeploy:

```
covid           301 -> https://torin.bg/new/about.html                    -> 200  hops=1
laptopi         301 -> https://torin.bg/new/index.html                    -> 200  hops=1
rezervni-chasti 301 -> https://torin.bg/new/ekran-klaviatura-portove.html -> 200  hops=1
za-bateriite    301 -> https://torin.bg/new/zalivane-technosti.html       -> 200  hops=1
```

**Cutover impact changed.** Promoting this block now requires TWO edits, not one: the
canonicalisation target *and* the `RewriteBase`. Both are named in the `.htaccess` header. 03.5-07's
audit must carry the pair, not the single edit the file previously described.
